When Netflix streamed the Paul vs. Tyson fight in November 2024, it reported 65 million concurrent streams, and many viewers saw buffering and freezes. The code that plays a video wasn't the problem. The hard part was everything around it: traffic spiking all at once, encoding pipelines, and delivery networks under a load nobody had tested at that size. System design is the discipline that deals with that layer.

System design is planning how a product works end to end under real conditions. You decide:

  • The building blocks: clients, load balancers, services, databases, caches, queues, CDNs.
  • How they interact: APIs, sync or async calls, data flow.
  • How it behaves at scale: traffic spikes, slow networks, failed machines, regional outages.
  • Which trade-offs to accept: cost or reliability, latency or consistency, simplicity or flexibility.

Design, coding and architecture

Coding asks "how do I implement this correctly?" System design asks "how does the whole system stay correct, fast and available when reality hits?" Coding failures are null pointers and logic bugs. Design failures are outages, cascading failures and data loss. Software architecture is the wider, longer-lived layer: the structure and principles shared across many systems in an organization. A specific system design works within that architecture.

Monolith or microservices

A monolith is one deployable unit. It's simple to build, test and debug, calls between parts are fast in-process function calls, and you scale it as one piece. Microservices split the product into independently deployable services, each owned by a team and scaled separately. You pay for that with network calls, data spread across services, and much more to operate. A common approach is to start with a well-structured monolith and split out services when team size or scale demands it.

Requirements come first

Functional requirements say what the system does: "users can upload a video". Non-functional requirements say how well it must do it: "p99 latency under 200 ms", "99.95% availability", "no data loss once an upload is confirmed". Non-functional requirements drive most design decisions.

Availability is the share of time a system does its job, usually written in "nines". It depends on how often things break (MTBF, mean time between failures) and how quickly you recover (MTTR, mean time to repair): availability = MTBF / (MTBF + MTTR). Halving recovery time helps as much as halving how often things break.

99.999%5.26 minutes26 seconds
  • In series (A calls B, and both must work): multiply. 99.9% × 99.9% = 99.8%. Every extra dependency lowers availability.
  • In parallel (any one of n copies is enough): 1 − (1 − A)n. Two 99% servers give 99.99%, assuming they fail independently. Shared power, shared configuration or shared deploys break that assumption.

Fault tolerance techniques: redundancy (active-active or active-passive), health checks with automatic failover, graceful degradation (show cached or partial results instead of an error), and limiting the blast radius with cells, availability zones and regions. In June 2019, a routine network configuration change at Google Cloud spread across regions and disrupted YouTube, Gmail and Google Cloud services for about four hours. Containing changes like that is part of the design.

Synchronous or asynchronous

In a synchronous call the caller waits for the answer. It's simple and gives immediate results, but the caller inherits the callee's latency and failures. In asynchronous communication the caller drops a message on a queue or log and moves on. Services are decoupled, spikes get absorbed and failures are contained. The cost is eventual results, harder debugging, and duplicates to handle.

Common patterns: request-response, fire-and-forget, publish-subscribe (one event, many consumers), event streaming (a durable, replayable log like Kafka), and for multi-step workflows, choreography (services react to each other's events) or orchestration (a central coordinator, as in sagas).

API styles

  • REST: resources and HTTP verbs. It's cacheable and universally understood, which makes it the default for public APIs.
  • GraphQL: a single endpoint where the client asks for exactly the fields it needs. It's great for many different clients. Caching and protecting against expensive queries are harder.
  • gRPC and RPC: typed contracts in Protocol Buffers over HTTP/2, which makes it fast, supports streaming and generates client code. It's common between internal services.

Serialization and protocols

JSON is readable but verbose. Protobuf, Avro and Thrift are compact binary formats with schemas. Evolve those schemas safely: add optional fields and never reuse field numbers. Underneath, TCP gives reliable, ordered streams and UDP gives fast, lossy packets, which suit voice, video and DNS. HTTP/2 sends many requests over one connection, HTTP/3 runs over QUIC on UDP, and WebSockets let the server push to the browser.

Storage types

  • Block storage provides raw volumes, like Amazon EBS or a local SSD. It's low latency, and databases run on it.
  • File storage is a shared hierarchical filesystem, like NFS or EFS, for workloads that expect files and folders.
  • Object storage holds immutable objects under flat keys behind an HTTP API, like S3 or GCS. It scales almost without limit and is designed for 99.999999999% durability. Use it for media, backups and data lakes.

SQL, NoSQL and NewSQL

Relational (SQL) databases offer schemas, joins and ACID transactions, like PostgreSQL and MySQL. NoSQL comes in families tuned for specific access patterns: key-value (Redis, DynamoDB), document (MongoDB), wide-column (Cassandra) and graph (Neo4j). Many favor BASE (Basically Available, Soft state, Eventually consistent) over ACID. NewSQL databases (Spanner, CockroachDB, TiDB) keep SQL and ACID while scaling horizontally with consensus.

Indexes

An index trades write speed and space for read speed. B-trees update pages in place, are read-optimized and handle range queries well. They're the default in relational databases. LSM trees buffer writes in memory, flush sorted files and merge them in the background, which makes them write-optimized (Cassandra, RocksDB). A composite index on (a, b) helps queries that filter on a, or on a and b, but not on b alone. Use EXPLAIN to check whether the query plan actually uses your index.

Spatial indexes

"Find drivers near me" needs 2D lookups. A quadtree splits a region into four cells whenever a cell holds too many points, so dense areas get fine cells and empty areas stay coarse. R-trees group nearby objects into bounding rectangles (PostGIS). Geohashes encode locations as strings, so nearby places share a prefix.

Vertical scaling means a bigger machine: simple, but there's a ceiling. Horizontal scaling means more machines. It's easy for stateless services behind a load balancer. Caching strategies

  • Cache-aside: the app checks the cache, and on a miss reads the database and fills the cache. This is the most common approach.
  • Write-through: each write goes to the cache and the database together. Reads are fresh, but writes are slower.
  • Write-back: writes go to the cache and reach the database later. Writes are fast, but you risk losing them.
  • Eviction: LRU (least recently used), LFU (least frequently used), or TTL expiry. A CDN is a cache at the network edge, close to users.

Related patterns: rate limiting (token bucket), CQRS (separate models for reads and writes), event sourcing (store the events and derive state from them), and change data capture (stream database changes to other systems).

Observability: metrics, logs, traces

  • Metrics are numbers over time. They're cheap to store and good for dashboards and alerts. Track RED for services (Rate, Errors, Duration) and USE for resources (Utilization, Saturation, Errors).
  • Logs are detailed records of individual events. Make them structured, as JSON with request IDs. They get expensive at high volume.
  • Traces follow one request across services using trace and span IDs (OpenTelemetry), so you can see which hop was slow.

An SLI is what you measure, such as the share of requests under 300 ms. An SLO is your target, such as 99.9% over 30 days. An SLA is a contract with penalties. The gap between 100% and your SLO is your error budget: while you have budget left, ship features. When it runs out, focus on reliability.

Track percentiles, not averages. An average of 50 ms can hide a p99 of 2 seconds. Tail latency also gets worse as requests fan out: if a page waits for 100 backends, the slowest one sets the page's speed.

Processes, threads, concurrency

A process has its own memory, which isolates it but makes it costly to create and to communicate with. Threads share their process's memory, which makes them cheap and fast to communicate between, but open to race conditions. Concurrency is handling many tasks over the same period by interleaving them. An event loop can do this on one core. Parallelism is running tasks at the same instant on several cores. Amdahl's law caps the speedup from parallelism: the part that must run serially limits you no matter how many cores you add. The OS scheduler and memory management (paging, the cost of context switches) set the per-machine limits you build on.

The CIA triad sets security goals: Confidentiality (only authorized parties can read), Integrity (data can't be changed without detection) and Availability (the system stays usable, including under attack).

  • Authentication answers "who are you?" with passwords plus MFA, passkeys, OpenID Connect, or mutual TLS between services. Authorization answers "what are you allowed to do?" with role-based or attribute-based access control. Apply least privilege.
  • Symmetric encryption (AES) uses one shared key and is fast. Asymmetric encryption (RSA, elliptic curves) uses a public and private key pair, for exchanging keys and making digital signatures. Hashing (SHA-256) is one-way and detects tampering. Store passwords with slow, salted hashes such as bcrypt or Argon2.
  • TLS uses asymmetric cryptography during the handshake to agree on symmetric session keys. The server proves who it is with a certificate signed by a trusted authority (PKI). Encrypt data in transit (TLS everywhere) and at rest (keys in a key management service).
  • OAuth 2.0 is delegated authorization. An app gets a limited, revocable access token instead of your password. OpenID Connect adds identity on top of it.

Whether it's an interview or a real design review, a repeatable process keeps you from missing the requirements that matter.

  1. Clarify requirements. Functional scope, non-functional targets, scale, and what's out of scope.
  2. Estimate. Back-of-envelope QPS, storage and bandwidth. They decide whether you need sharding or caching at all.
  3. Define the API. The main endpoints or events, with their inputs and outputs.
  4. Model the data. Entities, access patterns, and the choice of store.
  5. Sketch the high-level design. Clients, load balancers, services, storage, caches, queues.
  6. Deep dive. Bottlenecks, hot keys, failure modes, consistency choices.
  7. Discuss trade-offs. What you gave up and why, and what you'd change at 10× scale.

Choosing technology: match the access pattern first, then weigh how well your team knows it, how mature it is, what it costs to run, and whether a managed service fits. Boring technology you can operate usually beats exciting technology you can't.

Useful numbers: a day has 86,400 seconds, roughly 10⁵. One million requests a day is about 12 per second. Peak traffic is often 2–5× the average. Reads often outnumber writes 10:1 to 100:1.

A distributed system is a group of computers that work together over a network and look like one system to the people using it. Your bank, your favorite streaming service and the DNS lookup behind this page all work this way.

We distribute for three reasons. Scale: one machine can't hold all the data or serve all the traffic. Fault tolerance: if one machine dies, others carry on. Latency: putting copies near users in Tokyo and São Paulo makes requests faster for both.

The price is that three things you took for granted on one machine stop being true:

  • Partial failure. Some parts break while others keep running, and you often can't tell which is which.
  • An unreliable network. Messages get lost, delayed, duplicated or reordered.
  • No shared clock. Each machine has its own clock, and they drift apart. "What happened first?" becomes a hard question.

How we judge correctness: safety and liveness

Every guarantee in this course is one of two kinds. A safety property says something bad never happens, like "two nodes never both believe they are the leader". If it's broken, you can point to the exact moment it went wrong. A liveness property says something good eventually happens, like "every request eventually gets a reply". You can never catch it failing at one moment, because "eventually" might still be coming.

Most distributed algorithms protect safety at all times and give liveness only when the network behaves. Keep that pattern in mind. You'll see it again in CAP, Paxos and Raft.

In the 1990s, engineers at Sun Microsystems wrote down eight assumptions that programmers new to distributed systems tend to make. Every one of them is false, and every one has caused real outages. They're known as the fallacies of distributed computing.

Code written on one machine quietly relies on them. A function call always returns, takes nanoseconds, and nobody can intercept it. Swap the function call for a network call and all of that breaks.

How big is "latency"?

Nanoseconds are hard to picture. Scale the numbers so that one nanosecond becomes one second, and a round trip across the Atlantic takes years. This is why the number of network round trips is often the most important performance metric in a distributed design.

To reason about an algorithm you need to state what can go wrong. That statement is the system model. It has two parts: how nodes fail and how timing behaves.

How nodes fail

  • Crash-stop: the node halts and never comes back. This is the simplest case to reason about.
  • Crash-recovery: the node halts, then restarts, possibly having lost whatever was only in memory. Most real servers behave like this.
  • Omission: the node keeps running, but some messages it sends or receives are dropped.
  • Byzantine: the node does anything at all, including lying, because of bugs, corrupted hardware or an attacker. Blockchains and aircraft controls design for this. Most datacenter systems don't.

How timing behaves

  • Synchronous: messages and processing finish within known time bounds. This is easy to reason about, and it's rarely true.
  • Asynchronous: there are no time bounds at all. A slow node and a dead node look exactly the same.
  • Partially synchronous: the bounds hold most of the time but can be broken for a while. Nearly all practical algorithms, including Raft and Paxos, assume this.

The core problem: you can't tell a crashed node from a slow one. All you have is a timeout, and every timeout value is a guess.

Lab · Diagnose the failure

A client sends "charge $20" and hears nothing back. Maybe the request was lost. Maybe the server charged the card and the reply was lost. The client can't know which. This is the Two Generals problem: over an unreliable link, no amount of messaging gives both sides certainty.

That leaves three delivery guarantees:

  • At-most-once: send once and never retry. You get no duplicates, but some messages are lost.
  • At-least-once: retry until you get an acknowledgment. Nothing is lost, but some messages are processed twice.
  • Exactly-once: impossible as pure delivery. It's built as at-least-once delivery plus idempotent processing. The client attaches a unique ID to each request, and the server remembers which IDs it has already handled.

When Kafka or Flink advertise "exactly-once", they mean exactly-once effect, achieved through deduplication or transactions on top of retries.

When data outgrows one machine, you split it. Horizontal partitioning, also called sharding, puts different rows on different nodes. Each node owns a slice of the keys. (Vertical partitioning, which splits by column, is a separate technique.) The hard part is deciding which key goes where so that load stays even and resizing the cluster stays cheap.

  • Range partitioning: each node owns a key range, such as A–F. Range scans are fast. Hot spots are common, because many names start with "S" and every new timestamp lands on the last node.
  • Hash partitioning (hash mod N): node = hash(key) mod N. Load spreads evenly, but you lose range scans, and changing N moves almost every key.
  • Consistent hashing: nodes and keys sit on a ring, and each key belongs to the next node clockwise. Adding a node moves only its fair share of the keys, about 1/(N+1). Virtual nodes (many ring positions per node) smooth out the imbalance. Cassandra, Riak and the original Dynamo design use this.

Replication keeps copies of the same data on several nodes. You get availability (others take over), durability (data survives disk loss), read scaling, and lower latency for distant users. The hard part is keeping the copies in agreement.

  • Primary-backup (single leader): all writes go to one primary, which ships them to backups. With synchronous replication the primary waits for backups before confirming: safe, but slow, and one slow backup stalls everyone. With asynchronous replication it confirms immediately: fast, but backups lag, and a failover can lose confirmed writes. PostgreSQL, MySQL and MongoDB work this way.
  • Multi-primary: several nodes accept writes, which is useful across regions or offline. Concurrent writes conflict and need a resolution rule: last-write-wins, a custom merge, or CRDTs.
  • Leaderless: the client writes to several replicas directly and reads from several. Quorums decide what counts as success. This is the design from Amazon's 2007 Dynamo paper, covered in the next lesson.

In leaderless replication, each value lives on N replicas. A write succeeds when W of them confirm, and a read asks R of them, keeping the value with the newest version.

If R + W > N, every group of replicas you read from overlaps with every group that accepted the latest write, by the pigeonhole principle. At least one replica in your read has the newest value. If 2W > N, the two sides of a partition can't both accept writes, because only one side can gather W replicas. Concurrent writes that reach overlapping replicas can still both succeed and have to be resolved by version.

Lowering W or R makes requests faster and more failure-tolerant but allows stale reads. This is the PACELC trade-off you can tune per query: in Cassandra, ONE is fast and AP, while QUORUM is slower and consistent.

One caveat: quorum overlap alone doesn't give full linearizability. Read repair, sloppy quorums and clock-based conflict resolution all open gaps. The overlap is necessary but not sufficient.

The CAP theorem, proved by Gilbert and Lynch in 2002 after Eric Brewer's conjecture, involves three properties:

  • Consistency (C): every read returns the most recent completed write, or an error. Formally this is linearizability, which is stricter than the C in ACID.
  • Availability (A): every request to a non-failed node gets a non-error response.
  • Partition tolerance (P): the system keeps working even if the network drops messages between nodes.

The theorem says that during a network partition you can't have both C and A. A node cut off from the others must either refuse the request (losing A) or answer from its own possibly stale copy (losing C).

The popular "pick two" phrasing is misleading. Partitions aren't optional, so "CA" just describes a single-node system. When the network is healthy you can have both. PACELC extends the idea: if Partition, choose A or C; Else, choose Latency or Consistency.

    "Consistent" isn't a yes-or-no property. A consistency model defines which histories, meaning sequences of operations and the results clients observed, a system is allowed to produce. Model A is stronger than model B if it allows fewer histories. Stronger models are easier to build applications on, but they need more coordination, which costs latency and availability.

    • Linearizability: each operation appears to take effect at one instant between when it was sent and when it was confirmed. After a write is confirmed, every later read sees it. You can treat the system as a single copy, which is what makes locks, counters and compare-and-swap possible.
    • Sequential consistency: everyone sees all operations in the same order, and each client's own operations stay in program order. That order doesn't have to match real time, so a read can lag behind.
    • Causal consistency: only operations that are causally related must be seen in the same order, such as a reply and the comment it answers. Unrelated operations may appear in different orders to different clients. It's among the strongest models that can stay available during a partition, provided clients keep talking to the same replica.
    • Eventual consistency: if writes stop, all replicas eventually converge. Until then, almost any order or stale value is possible.

      Lab · Judge the history

      Each history shows when an operation started and finished, measured in ms. Is it linearizable? Ask yourself whether you can pick one instant inside each operation's interval so that the results make sense for a single copy of x, which starts at 0.

      Consistency models describe single operations on replicated data. Isolation levels describe what concurrent transactions can see of each other. They're the I in ACID:

      • Atomicity: all of a transaction's writes happen, or none do.
      • Consistency: application rules, like "balances never go negative", hold before and after. This is mostly the application's job.
      • Isolation: concurrent transactions don't interfere. At the strongest level, serializable, the result matches some one-at-a-time order.
      • Durability: once committed, the data survives crashes.

      Weaker isolation levels are faster but allow anomalies. Defaults differ: PostgreSQL uses Read Committed, MySQL's InnoDB uses Repeatable Read, and Oracle's "serializable" is actually snapshot isolation.

      How databases enforce isolation

      • Pessimistic (two-phase locking): take locks and hold them until commit. Correct, but readers and writers block each other, and deadlocks happen.
      • Optimistic (OCC): run without locks, check for conflicts at commit, and abort if any are found. Works well when conflicts are rare.
      • MVCC snapshots: each transaction reads a consistent snapshot, so readers never block writers. This gives snapshot isolation. Serializable Snapshot Isolation (PostgreSQL's SERIALIZABLE) adds detection of dangerous read-write patterns on top.

      The overall picture: in distributed databases, strict serializability means serializable plus linearizable. Spanner and FoundationDB provide it, and it's the strongest guarantee you can get.

      A transaction that touches several nodes, say Orders, Payments and Inventory, must commit everywhere or nowhere. This is atomic commitment.

      Two-phase commit (2PC)

      1. Prepare: the coordinator asks every participant "can you commit?". A participant that votes yes writes everything durably and promises to commit if told to. From then on it can't decide by itself.
      2. Commit or abort: if every vote is yes, the coordinator logs COMMIT and tells everyone. If any vote is no or a participant times out, it tells everyone to abort.

      The weak point: if the coordinator crashes after participants voted yes, they're in doubt. They can't commit or abort, and they keep holding locks until the coordinator returns. 2PC is blocking.

      • Three-phase commit (3PC) adds a "pre-commit" round so participants can finish without the coordinator. It works only with bounded network delays, and a partition can still make it inconsistent, so it's rarely used.
      • Consensus-based commit replicates the coordinator's decision with Paxos or Raft, so the crash of one machine can't block the transaction. Spanner and CockroachDB do this.
      • Sagas handle long-running workflows across services. They're a chain of local transactions, each with a compensating action that undoes it. A saga gives up isolation, and other services can see the intermediate states.

      Make this step fail:

      Consensus is getting several nodes to agree on one value, despite failures. A correct algorithm guarantees:

      • Agreement: no two nodes decide different values. (Safety.)
      • Validity: the decided value was proposed by some node. (Safety.)
      • Termination: every node that doesn't crash eventually decides. (Liveness.)

      Agree on a sequence of values, one log entry at a time, and you get a replicated state machine. Every node applies the same commands in the same order, so they all end up in the same state. That's how etcd, ZooKeeper, Consul and CockroachDB keep their replicas identical.

      FLP impossibility

      In 1985, Fischer, Lynch and Paterson proved that in a fully asynchronous system, no deterministic algorithm can guarantee consensus if even one node may crash. The reason is the same problem as before: you can't tell slow from dead. Real algorithms keep safety at all times and give up termination only while the network misbehaves, relying on timeouts and randomness to get unstuck.

      Paxos and Raft

      Paxos (Lamport) uses numbered proposals. A proposer first gets promises from a majority to ignore older proposals, then asks that majority to accept a value, adopting any value that might already have been chosen. Any two majorities overlap, so two different values can never both be chosen. Multi-Paxos runs the protocol with a stable leader for efficiency.

      Raft (Ongaro and Ousterhout, 2014) was designed to be easier to understand and splits the problem into parts:

      • Leader election: time is divided into terms. A follower that hears nothing from a leader before its randomized timeout becomes a candidate, starts a new term and asks for votes. A majority makes it leader.
      • Log replication: the leader appends client commands to its log and sends them to followers. An entry is committed once a majority store it. (Subtlety: a leader only commits this way for entries from its current term; older entries become committed along with them.)
      • Safety: a node only votes for a candidate whose log is at least as up to date as its own, so a new leader always has every committed entry.

      Physical clocks drift. A typical quartz crystal is off by about 20 parts per million, close to 2 seconds a day. NTP corrects them to within a few milliseconds over the internet, but clocks can still jump backward after a sync or a leap second. Sorting events by wall-clock time across machines is unreliable. Spanner gets around this with GPS and atomic clocks plus explicit uncertainty intervals (TrueTime), and it waits out the uncertainty before committing.

      Happened-before

      Lamport (1978) defined order without clocks. Event a happened before b (a → b) if a and b are on the same process and a came first, or if a sends a message and b receives it, or if this follows by chaining (transitivity). If neither a → b nor b → a, the events are concurrent. That doesn't mean they happened at the same instant, only that neither could have influenced the other.

      • Lamport clock: one counter per process. Add 1 on every event. On receiving a message, set the counter to max(local, received) + 1. If a → b then L(a) < L(b), but the converse doesn't hold: a smaller number doesn't prove a happened first.
      • Vector clock: one counter per process, kept as a vector. On receiving a message, take the element-wise maximum, then add 1 to your own entry. Now a → b if and only if V(a) < V(b). If neither vector is less than the other, the events are concurrent.
      • Version vectors apply the same idea to versions of a data item, so replicas can tell "newer" from "conflicting". Riak and the original Dynamo use them. Dotted version vectors fix the problem of siblings piling up when many clients write.
      • Distributed snapshots (Chandy-Lamport) use marker messages to record a consistent global state without stopping the system. Flink builds its checkpoints this way.

      Theory tells you what's possible. Production adds gray failures, overload, deploys and humans. These patterns show up in almost every reliable system:

      • Timeouts everywhere. A call without a timeout can wait forever. Set the timeout from measured latency percentiles, such as p99.9.
      • Retries with exponential backoff and jitter. Retry transient errors, wait longer each time, and randomize the wait so thousands of clients don't retry at the same moment.
      • Idempotency keys. Make retries safe, as in the delivery lesson.
      • Circuit breakers. After repeated failures, stop calling a dependency for a while. Failing fast protects both sides.
      • Bulkheads. Give each dependency its own thread pools and connection limits, so one slow service can't use up every resource.
      • Backpressure and load shedding. When overloaded, push back on producers or reject low-priority work early. Queues that never fill up hide problems until memory runs out.
      • Leases and fencing tokens. Grant time-limited ownership, and have storage reject writes that carry an outdated token.
      • Backward-compatible changes. Old and new versions run side by side during every deploy. Change schemas and APIs in steps: add, migrate, then remove.

      Failure modes to design for

      Real systems combine everything in this course. The labels below describe default behavior, and most systems can be configured to lean the other way. PACELC: during a Partition choose A or C; Else choose Latency or Consistency.

      • GFS and HDFS split files into large chunks of 64–128 MB, replicated three times. A single master holds the metadata. They're optimized for appends and big sequential reads, and GFS's relaxed consistency let concurrent appends produce duplicates.
      • ZooKeeper runs the ZAB consensus protocol to give linearizable writes and ordered reads. Locks, leader election and configuration are built from its small primitives: ephemeral and sequential znodes plus watches.
      • BigTable and HBase divide a sorted key space into regions, each served by one server, which gives strong consistency per row. Data lands in a write-ahead log and memtable, then is flushed to immutable SSTables.
      • Cassandra is leaderless with consistent hashing and gossip, and you choose a consistency level per query. Its lightweight transactions use Paxos for compare-and-set.
      • Spanner combines Paxos groups per shard, 2PC across shards and TrueTime timestamps to provide externally consistent (strictly serializable) global transactions.
      • Kafka stores partitioned, replicated logs. Producers choose acks, and idempotent producers plus transactions give exactly-once effect within Kafka.
      • MapReduce, Spark and Flink recover from failure by re-running deterministic tasks. Spark recomputes from lineage, and Flink restores from Chandy-Lamport-style checkpoints and uses watermarks to handle events that arrive late.
